Module 01 — Foundations

Classes, Objects, and the Blueprint Metaphor

What is a class, really?

A class is a blueprint that describes what data (attributes) and behavior (methods) something will have. It doesn't do anything by itself — it's a drawing on paper. An object (or instance) is the actual house built from that blueprint. You can build many houses from one blueprint, and each one is independent: painting house A blue doesn't repaint house B.

Analogy
A cookie cutter (the class) defines the shape. Every cookie you stamp out (the object) has that shape, but each cookie is a separate piece of dough — decorate one with sprinkles and the others stay plain. 
class Dog:
    def __init__(self, name, breed):
        self.name = name        # attribute
        self.breed = breed      # attribute

    def bark(self):             # method
        return f"{self.name} says Woof!"

rex = Dog("Rex", "Labrador")    # instantiation
print(rex.bark())               # "Rex says Woof!"

__init__ is the constructor — Python calls it automatically the moment you create an object, to set up its starting attributes. self is how a method refers to "this particular object" — it's the difference between the blueprint and the specific house being worked on.

Instance vs. class attributes

FeatureInstance attributeClass attribute
DefinedInside __init__ with self.Directly in the class body
Shared?Unique per objectShared by all instances (unless overridden)
Use caseData that varies per object (name, balance)Constants or counters shared across all (species, total count)
Common misconception
"A class is the same thing as an object." No — the class is the definition; the object is a specific realization of it in memory. You can have zero, one, or a million objects from a single class.
Exercise: draft a blueprint

Write a Car class with attributes make and year, and a method describe() that returns a string like "2021 Toyota".


Hint: self.make = make and self.year = year go inside __init__; describe can use an f-string.
Key takeaways
  • A class defines structure; an object is a specific instance with its own data.
  • __init__ runs automatically to initialize a new object.
  • self refers to the specific object a method is operating on.
  • Instance attributes vary per object; class attributes are shared.

Module 02 — Structural Design

Encapsulation and Access Control

Hiding the wiring behind the wall

Encapsulation means bundling data with the methods that operate on it, and controlling how outside code can touch that data. Python doesn't have true "private" enforcement — instead it uses naming conventions and properties to signal intent and add validation.

Analogy
A building's electrical wiring is inside the walls, not exposed. You interact with a light switch (the public interface), not the raw wires (internal state). This protects you from shocks and protects the wiring from being messed with incorrectly. 
class BankAccount:
    def __init__(self, balance):
        self._balance = balance      # convention: "protected"

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit must be positive")
        self._balance += amount

acct = BankAccount(100)
acct.deposit(50)
print(acct.balance)   # 150 — read-only from outside
ConventionSyntaxMeaning
Publicself.nameFreely accessible, part of the intended API
Protectedself._name"Internal use" signal, still accessible
Private (name-mangled)self.__namePython renames it internally to discourage accidental access
Common misconception
"Double underscore makes an attribute truly private, like Java." Python only name-mangles it (to _ClassName__name) — it's a deterrent, not a lock. Discipline and conventions do the real work.
Exercise: add validation

Extend BankAccount with a withdraw(amount) method that raises a ValueError if amount is greater than the balance.


Hint: compare amount to self._balance before subtracting.
Key takeaways
  • Encapsulation bundles data and behavior, and controls access to protect invariants.
  • Python signals privacy with underscores rather than enforcing it strictly.
  • @property lets you expose controlled, computed, or read-only access.

Module 03 — Practical Application

Inheritance and Polymorphism

Extending blueprints, and shared behavior with different results

Inheritance lets a new class (child) reuse and extend an existing class (parent) instead of rewriting everything. Polymorphism means objects of different classes can respond to the same method call in their own way.

Analogy
A "Building" blueprint has foundations, walls, and a roof. A "House" and an "Office" blueprint both start from "Building" and add their own rooms. Ask any building to open_main_entrance() and each does it appropriately — a house unlocks a front door, an office runs a badge scanner — same instruction, different response. 
class Animal:
    def __init__(self, name):
        self.name = name
    def speak(self):
        raise NotImplementedError

class Dog(Animal):
    def speak(self):
        return f"{self.name}: Woof!"

class Cat(Animal):
    def speak(self):
        return f"{self.name}: Meow!"

for a in [Dog("Rex"), Cat("Momo")]:
    print(a.speak())    # polymorphism: same call, different output

Use super().__init__(...) inside a child's constructor to run the parent's setup before adding the child's own attributes:

class Puppy(Dog):
    def __init__(self, name, age_months):
        super().__init__(name)
        self.age_months = age_months
Common misconception
"Inheritance is always the right way to reuse code." Overusing inheritance creates rigid hierarchies. If the relationship is "has-a" rather than "is-a" (an Engine isn't a kind of Car), prefer composition — give the object an instance of another class instead of extending it.
Exercise: extend the hierarchy

Create a Bird(Animal) class whose speak() returns "{name}: Tweet!", then write a loop that calls speak() on a list containing a Dog, Cat, and Bird.


Hint: override speak exactly like Dog and Cat did — same method name, new class.
Key takeaways
  • Inheritance models "is-a" relationships and lets children reuse/extend parent behavior.
  • Polymorphism lets the same method call behave differently depending on the object's class.
  • super() calls the parent implementation from a child.
  • Prefer composition over inheritance for "has-a" relationships.

Module 04 — Mastery

Dunder Methods, Composition, and Design Judgment

Making objects behave like built-ins

Dunder (double-underscore) methods let your objects plug into Python's own syntax — printing, comparison, arithmetic, length. This is how len(my_list) and "a" + "b" work under the hood, and you can give your own classes the same powers.

class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __repr__(self):
        return f"Vector({self.x}, {self.y})"
    def __add__(self, other):
        return Vector(self.x + other.x, self.y + other.y)
    def __eq__(self, other):
        return self.x == other.x and self.y == other.y

v1, v2 = Vector(1, 2), Vector(3, 4)
print(v1 + v2)          # Vector(4, 6)
print(v1 == Vector(1,2)) # True
DunderTriggered byPurpose
__init__ClassName(...)Initialize a new object
__repr__print(), consoleDeveloper-friendly representation
__add__a + bCustom arithmetic
__eq__a == bCustom equality logic
__len__len(a)Custom length

Composition: building with parts, not just extending

Analogy
A house "has an" electrical system, a plumbing system, and a roof — it isn't a specialized kind of any of them. Composition assembles a class from other objects as attributes, rather than inheriting from them. 
class Engine:
    def start(self):
        return "Engine running"

class Car:
    def __init__(self):
        self.engine = Engine()      # "has-a" Engine
    def start(self):
        return self.engine.start()
Common misconception
"More dunder methods and deeper hierarchies = better design." Mastery is knowing when not to reach for OOP machinery. A simple function is often clearer than a class with one method; a flat structure often beats a five-level hierarchy.
Exercise: give Vector a magnitude

Add a __len__ (or a regular magnitude() method) to Vector that returns the rounded distance from the origin using (x**2 + y**2) ** 0.5.


Hint: return (self.x**2 + self.y**2) ** 0.5
Key takeaways
  • Dunder methods integrate your objects with Python's built-in syntax and functions.
  • Composition models "has-a" relationships and is often more flexible than inheritance.
  • Good OOP design is about judgment — using the simplest structure that models the problem.

Summary Notes

Object-oriented programming organizes code around objects that bundle data and behavior. Classes are the blueprints; instances are the built objects. Encapsulation protects internal state behind a controlled interface. Inheritance reuses behavior across an "is-a" hierarchy, while polymorphism lets different classes respond to the same call in their own way. Composition assembles objects from other objects for "has-a" relationships, and is often the more flexible choice. Dunder methods let custom objects integrate naturally with Python's syntax. The mark of mastery isn't using every OOP feature — it's choosing the simplest structure that honestly models the problem.
