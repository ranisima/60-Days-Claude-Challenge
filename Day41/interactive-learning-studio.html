Module 01 · Foundational

Classes, Objects & the Blueprint Mindset

Where OOP thinking begins: turning "a function that operates on a dict" into "an object that knows things and does things."

Explain Why bother with objects?

In procedural code, data and the functions that act on it live apart — you pass a dictionary into function after function, hoping everyone agrees on its shape. OOP fuses the two: a class defines the shape of the data (attributes) and the behavior that belongs to it (methods) in one place. An object (or instance) is one concrete thing built from that class.

Analogy
A class is an architectural blueprint for a house — it specifies "there will be a front_door, a roof_color, and a way to open_door()." No one lives in the blueprint. Each house built from it — 12 Elm Street, 8 Baker Street — is an object: a specific instance with its own roof_color, but the same underlying structure.

Example Your first class

class Dog:
    # __init__ runs once, when an object is being built
    def __init__(self, name, breed):
        self.name = name        # instance attribute
        self.breed = breed
        self.energy = 100

    def bark(self):
        return f"{self.name} says Woof!"

    def play(self):
        self.energy -= 10
        return f"{self.name} is playing. Energy: {self.energy}"

rex = Dog("Rex", "Labrador")   # instantiation
mia = Dog("Mia", "Poodle")

print(rex.bark())    # Rex says Woof!
print(mia.play())    # Mia is playing. Energy: 90

self is simply "the object this method was called on." When you write rex.bark(), Python translates it to Dog.bark(rex) behind the scenes — self is rex inside that call. That's why rex.energy and mia.energy stay independent: each object owns its own copy of the attributes set in __init__.

Exercise Predict, then check

Try it yourself

Given the Dog class above, what does this print?

a = Dog("Zeus", "Husky")
b = Dog("Zeus", "Husky")
print(a is b)
print(a.name == b.name)
False, then True. a is b is False because is checks object identity — two separate Dog() calls create two separate objects in memory, even with identical arguments. a.name == b.name is True because == compares values, and both names are the string "Zeus".

Misconceptions

Misconception
"A class and an object are the same thing." — A class is the definition; an object is one instance built from it. You can make thousands of objects from a single class.
Misconception
"self is a Python keyword." — It's just a convention (a regular parameter name). Python doesn't require the name self, but every style guide and every other developer expects it, so don't rename it.
Key Takeaways
  • A class defines structure + behavior; an object is a concrete instance of it.
  • __init__ runs automatically on creation and sets up instance attributes via self.
  • Each object has its own independent copy of instance attributes.
  • Methods are just functions defined inside a class that automatically receive the object as self.
Module 02 · Core Pillars

Encapsulation, Inheritance, Polymorphism, Abstraction

The four ideas that every OOP explanation eventually circles back to — here's what each one actually buys you.

Explain Encapsulation: bundling + gatekeeping

Encapsulation means two things at once: (1) bundling data and the methods that operate on it together, and (2) controlling access to that data so outside code can't put it in an invalid state. Python doesn't have true "private" attributes — it uses convention instead of enforcement.

class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance   # _single underscore = "internal, please don't touch"

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("Deposit must be positive")
        self._balance += amount

    def withdraw(self, amount):
        if amount > self._balance:
            raise ValueError("Insufficient funds")
        self._balance -= amount

    @property
    def balance(self):
        return self._balance   # read-only view from outside

Nothing physically stops acct._balance = -500, but the leading underscore signals "this is an implementation detail — go through deposit()/withdraw() instead." A double underscore (__balance) triggers name mangling (becomes _BankAccount__balance), which discourages accidental access even more strongly, mainly to avoid clashes in subclasses.

Analogy
Encapsulation is a car's dashboard, not its engine bay. You press the accelerator (a public method); you don't reach in and manually adjust the fuel injectors (a private attribute). The dashboard exposes a safe, simple interface over dangerous internal machinery.

Explain Inheritance: sharing a blueprint's structure

Inheritance lets one class (the subclass/child) reuse and extend another's (the superclass/parent) attributes and methods, expressing an "is-a" relationship.

class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} makes a sound"

class Cat(Animal):          # Cat "is an" Animal
    def speak(self):        # overrides the parent method
        return f"{self.name} says Meow"

class Robot(Animal):
    def __init__(self, name, model):
        super().__init__(name)   # reuse the parent's setup
        self.model = model

Explain Polymorphism: same call, different behavior

Polymorphism means code written against a general interface (like .speak()) works correctly no matter which specific subclass the object actually is — Python resolves the right method at runtime.

animals = [Cat("Tom"), Robot("Wall-E", "WE-100")]
for a in animals:
    print(a.speak())   # each object answers in its own way
# Tom says Meow
# Wall-E makes a sound   (Robot didn't override speak — inherits Animal's)

Explain Abstraction: hiding the "how"

Abstraction means exposing what something does while hiding how it does it. Every method you call — list.sort(), str.upper() — is abstraction: you don't need to know the sorting algorithm to use it. Python formalizes this with abc.ABC (covered fully in Module 4).

Misconception
"Inheritance is always the right way to reuse code." — Overusing inheritance creates rigid, deeply nested hierarchies. "Composition over inheritance" (build objects out of other objects) is often more flexible — covered in Module 3.
Misconception
"Polymorphism requires inheritance." — Python uses duck typing: if an object has a .speak() method, it works in the loop above regardless of its class hierarchy. "If it walks like a duck and quacks like a duck..."
Key Takeaways
  • Encapsulation controls access via naming convention, not hard enforcement.
  • super() lets a subclass reuse (not just override) parent behavior.
  • Polymorphism means the same method call produces type-appropriate behavior.
  • Abstraction is about designing a clean "what," hiding a messy "how."
Module 03 · Practical Application

The Working Toolkit: Dunder Methods, Properties, Composition

The features that separate "I know classes" from "I write idiomatic Python classes."

Explain Dunder (magic) methods

Methods surrounded by double underscores let your objects hook into Python's built-in syntax — +, len(), print(), comparisons — instead of requiring custom-named methods that no one but you will remember.

class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):                 # used by print(), debuggers
        return f"Vector({self.x}, {self.y})"

    def __add__(self, other):           # powers the + operator
        return Vector(self.x + other.x, self.y + other.y)

    def __eq__(self, other):            # powers ==
        return (self.x, self.y) == (other.x, other.y)

    def __len__(self):
        return int((self.x**2 + self.y**2) ** 0.5)

v1, v2 = Vector(1,2), Vector(3,4)
print(v1 + v2)      # Vector(4, 6)  — reads naturally
print(v1 == Vector(1,2))  # True
Analogy
Dunder methods are universal power outlets. Any appliance (object) with the right plug shape (__add__, __len__) works with the house's existing wiring (+, len()) — you don't need a custom socket (a uniquely-named method) for every device.

Explain Properties: computed attributes that look like data

class Circle:
    def __init__(self, radius):
        self.radius = radius

    @property
    def area(self):
        return 3.14159 * self.radius ** 2

    @radius = property.setter   # (conceptual — see setter pattern below)

c = Circle(4)
print(c.area)   # 50.26  — called with NO parentheses, looks like an attribute

A cleaner setter pattern: define @property for the getter, then @radius.setter for a method of the same name to validate assignment — letting you write c.radius = 10 while still running your own checks behind the scenes.

Compare Instance, class, and static methods

Instance methodselfNeeds to read/modify a specific object's data

class Pizza:
    def __init__(self, toppings):
        self.toppings = toppings

    @classmethod
    def margherita(cls):              # alternative constructor
        return cls(["tomato", "mozzarella"])

    @staticmethod
    def is_vegetarian(topping):        # no self/cls needed
        return topping not in ("pepperoni", "ham")

p = Pizza.margherita()   # no need to build the list yourself

Explain Composition over inheritance

Instead of forcing an "is-a" relationship, composition builds an object out of other objects — a "has-a" relationship. It's usually more flexible than deep inheritance chains.

class Engine:
    def start(self): return "Vroom"

class Car:
    def __init__(self):
        self.engine = Engine()   # Car HAS-A Engine, is not an Engine

    def start(self):
        return self.engine.start()

Exercise Write a dunder method

Coding challenge

Given a Money class with a cents attribute, write __str__ so that print(Money(1050)) outputs $10.50.

def __str__(self): return f"${self.cents // 100}.{self.cents % 100:02d}" — note __str__ (not __repr__) is what print() and str() prefer; __repr__ is the fallback for unambiguous debugging output.
Misconception
"@staticmethod and a regular module-level function are pointless to distinguish." — A static method is namespaced under the class (Pizza.is_vegetarian(...)), which documents that it's conceptually related, and it's inherited/overridable by subclasses, unlike a bare function.
Misconception
"You need getters and setters for every attribute, like in Java." — In Python, start with plain public attributes. Only add @property when you actually need validation or computed logic — adding boilerplate getters/setters upfront is considered unpythonic.
Key Takeaways
  • Dunder methods let objects integrate with Python's built-in operators and functions.
  • @property exposes computed values with attribute-style access; pair with @x.setter for validation.
  • Use @classmethod for alternative constructors, @staticmethod for related utility logic.
  • Prefer composition ("has-a") over deep inheritance when relationships aren't truly "is-a".
Module 04 · Mastery

Abstract Classes, Multiple Inheritance, Mixins & Dataclasses

The tools that let you design robust, extensible systems — and know exactly why Python resolves ambiguity the way it does.

Explain Abstract Base Classes

An ABC defines a contract — a set of methods subclasses must implement — without providing full implementations itself. It formalizes abstraction: you can't accidentally instantiate an incomplete class.

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...

    @abstractmethod
    def perimeter(self): ...

class Square(Shape):
    def __init__(self, side): self.side = side
    def area(self): return self.side ** 2
    def perimeter(self): return self.side * 4

Shape()    # TypeError: Can't instantiate abstract class Shape
Square(4)  # fine — all abstract methods implemented

Explain Multiple inheritance & the MRO

Python allows a class to inherit from more than one parent. When two parents define the same method, Python decides which one wins using the Method Resolution Order (MRO) — computed via the C3 linearization algorithm, viewable with ClassName.__mro__.

class Flyer:
    def move(self): return "flies"

class Swimmer:
    def move(self): return "swims"

class Duck(Flyer, Swimmer):   # left-to-right priority
    pass

print(Duck().move())         # "flies" — Flyer listed first
print(Duck.__mro__)          # (Duck, Flyer, Swimmer, object)

Explain Mixins: single-purpose, reusable behavior

A mixin is a small class not meant to stand alone — it exists purely to be combined with others via multiple inheritance, injecting one focused capability.

class JSONMixin:
    def to_json(self):
        import json
        return json.dumps(self.__dict__)

class User(JSONMixin):
    def __init__(self, name): self.name = name

User("Ada").to_json()   # '{"name": "Ada"}'  — capability "mixed in"

Explain Dataclasses: less boilerplate for data-holding classes

from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int
    # __init__, __repr__, and __eq__ are auto-generated

print(Point(1, 2))              # Point(x=1, y=2)
print(Point(1,2) == Point(1,2))  # True
Analogy
Mixins are like Lego attachments, not full Lego sets. A "Wheels" mixin snaps onto a Car, a Skateboard, or a RobotDog — it doesn't dictate what the whole object is, only that it can now roll.

Compare When to reach for what

ToolUse it when...
ABC + @abstractmethodYou must guarantee subclasses implement specific methods

Exercise Trace the MRO

Reasoning challenge

class C(A, B): pass — both A and B define greet(). Which one runs on C().greet(), and why?

A's greet() runs. Python's MRO walks the parent list left-to-right as written in the class definition (class C(A, B)), so A is checked before B. Confirm with C.__mro__.
Misconception
"Multiple inheritance is always risky and should be avoided entirely." — Deep, tangled multiple inheritance is risky. Shallow multiple inheritance via focused mixins (each adding one capability, none overlapping) is a standard, safe Python pattern.
Misconception
"@dataclass replaces regular classes entirely." — Dataclasses shine for data containers. Classes with rich behavior, invariants, or inheritance-heavy designs often still read better as regular classes.
Key Takeaways
  • ABC + @abstractmethod enforces a contract subclasses must fulfill.
  • The MRO resolves multiple-inheritance conflicts left-to-right via C3 linearization.
  • Mixins inject one focused, reusable capability without implying a full "is-a" relationship.
  • @dataclass auto-generates boilerplate for data-centric classes.
Final Challenge

Build a Small Shape Hierarchy

Apply everything: abstraction, inheritance, polymorphism, dunder methods, and a mixin — in one design.

SPEC-004 · Final ChallengeEst. 15–20 min

Design a small library for 2D shapes:

  1. An abstract Shape base class with abstract area() and perimeter().
  2. Circle and Rectangle subclasses implementing both.
  3. A ComparableMixin that implements __lt__ using self.area(), so shapes can be sorted with sorted(shapes).
  4. A __repr__ on Shape so print(shapes) is readable.
  5. Prove it works: build a list of mixed shapes and print them sorted by area.
Your solution
from abc import ABC, abstractmethod class ComparableMixin: def __lt__(self, other): return self.area() < other.area() class Shape(ABC, ComparableMixin): @abstractmethod def area(self): ... @abstractmethod def perimeter(self): ... def __repr__(self): return f"{type(self).__name__}(area={self.area():.1f})" class Circle(Shape): def __init__(self, r): self.r = r def area(self): return 3.14159 * self.r ** 2 def perimeter(self): return 2 * 3.14159 * self.r class Rectangle(Shape): def __init__(self, w, h): self.w, self.h = w, h def area(self): return self.w * self.h def perimeter(self): return 2 * (self.w + self.h) shapes = [Circle(3), Rectangle(2, 5), Circle(1)] print(sorted(shapes)) # [Circle(area=3.1), Rectangle(area=10.0), Circle(area=28.3)]
